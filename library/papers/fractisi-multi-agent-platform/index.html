When Many Coding Agents Share One Repo, Can Coordination Beat More Branches?

Short answer: Yes. As product architecture: coordination, shared project state, composition, Git awareness, and deploy approvals can beat unbounded private branching when agents share one repo — without claiming a production multi-vendor bake-off.

Gaps addressed by this evolution

  • Agent registration, lifecycle, permissions, capacity
  • Shared project representation + task ownership + dependencies
  • Conflict / interference detection (path + interface markers)
  • Composition engine with proposed→validated→integrated→deployed states
  • Git awareness and scoped workspaces (virtual by default; optional worktrees)
  • Deploy approvals (never unvalidated)
  • Adapter interface for Cursor / Claude Code / VS Code / OpenAI
  • Commercial tiers as entitlements of one product
  • Plug-and-play init + config templates + Docker self-host option
  • Comparative A/B/C coordination benchmark (measured simulation)

Reusable components extended (not replaced)

  • src/engine/gateway.mjs — execution core inside createPlatform()
  • src/sdk/index.mjs — now also exports createPlatform
  • src/cli/* — additive commands (init, status, agents, compose, coord-bench)
  • Layer gate — new platform layer between engine and sdk

Known limitations / remaining work

  • Adapters normalize messages; they do not yet drive live Cursor/Claude sessions.
  • Composition semantic analysis is marker/heuristic-based, not full program analysis.
  • Deploy connectors are approval-gated stubs (no cloud provider ship in this phase).
  • Comparative bench is an in-process measured simulation — not GPU/$ production cost.
  • 100-agent runs are supported in code paths but heavy host timing varies; default bench uses 5/10/25 (+50 with --full).
