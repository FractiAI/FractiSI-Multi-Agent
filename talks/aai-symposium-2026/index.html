Thank you to the Active Inference Institute for inviting us to participate in this symposium.

The purpose of this gathering is to bring together people exploring Active Inference and related approaches to understanding and building systems that can perceive, infer, learn, and act in complex environments.

Our work with FractiSI Multi-Agent approaches a related challenge from the computational architecture side. We’ve been exploring how to coordinate increasing numbers of AI agents that must work together on a shared, continuously changing problem.

What we discovered is that the challenge isn’t simply making individual agents more capable. It is also how we represent and coordinate the shared world in which those agents operate.

Today I’d like to introduce FractiSI Multi-Agent and present the architecture and experiments we’ve developed around that problem. In particular, we’ll look at what happens when multiple agents can operate over a shared computational world rather than repeatedly maintaining overlapping representations of it.

We’ll examine not only resource efficiency, but whether this architectural change can improve coordination, speed, accuracy, convergence, and ultimately the number of useful agents we can support within a given computational budget.

So this is both an introduction to FractiSI Multi-Agent and an invitation to explore whether this approach offers a useful contribution to the broader problem of building systems capable of coordinated inference and action. Let’s begin with the problem that led us there.

Part I · Introduction and context

The multi-agent opportunity

  • From one assistant → specialized agent collectives
  • Researchers, planners, programmers, reviewers, analysts, safety
  • More agents → share, coordinate, avoid duplication, compose
  • Hidden tax: the same world reproduced in every context

Intelligence at the agent level can raise collective overhead.

AI is moving beyond individual assistants toward systems of specialized agents. Instead of asking one model to perform every task, we can distribute work among multiple agents. We can have researchers, planners, programmers, reviewers, analysts, safety monitors, and specialized domain experts. Each agent can bring different capabilities to the problem.

This is a powerful direction. But as we increase the number of agents, we introduce another challenge. Those agents must share information, coordinate their activities, understand changes, avoid duplicating work, and combine their contributions into useful results. The more complex the problem becomes, the more important coordination becomes.

And there is an architectural issue hiding underneath all of this. Many of these agents are working on the same underlying information. Yet our systems frequently reproduce that information across their individual contexts and memories. We are increasing intelligence at the agent level, but we may also be increasing the overhead required to coordinate the collective. That is the problem FractiSI addresses.

Imagine five agents working on the same software engineering project. One investigates a problem. One examines the architecture. One writes code. One tests the implementation. One reviews security. They have different responsibilities, but they are all dealing with the same repository.

They need to understand many of the same things: the current files and their relationships, the architecture, dependencies, existing functionality, recent modifications, test results, outstanding issues.

In a conventional architecture, each agent may independently retrieve, reconstruct, summarize, and maintain overlapping portions of this information. They then exchange messages to keep one another informed. This creates several kinds of overhead: duplicated information; repeated retrieval and processing; communication overhead; the possibility that agents operate on different versions of what they believe is happening; and additional work to reconcile those differences.

The fundamental observation is simple: there may be many agents, but there is only one underlying project. Why should every agent have to independently reconstruct so much of it?

A different architectural approach

One shared world,

Agents keep objectives and local context. The shared substrate is not recopied for each.

This is where FractiSI enters the picture. FractiSI separates the shared computational world from the individual agents operating within it. Instead of treating every agent as an independent container for its own overlapping representation of the environment, we establish a shared substrate.

Agents access the information relevant to their responsibilities. They maintain their own objectives, reasoning, specialized knowledge, and working context. But the underlying shared information does not need to be independently recreated for each agent.

Think of it this way — conventional approach: one world, many independently maintained representations. FractiSI approach: one shared world, many specialized participants. This is not about making every agent identical. It is about allowing different agents to operate over common information without requiring each one to own a separate copy of everything. The architecture is designed to make that distinction practical.

How FractiSI Multi-Agent works

  3. Agents — models, tools, instructions, roles
  • Shared state ≠ agent-private objectives, reasoning, local context

Open · Multi-Agent paper · Tiny Gateway · Platform architecture

The product has several architectural elements. At the foundation is the shared computational world. Above that is Tiny Footprint, powered by Tiny Gateway. Tiny Gateway provides the compact access and coordination mechanism through which agents interact with the shared substrate. Above that are the agents.

These agents can use different models, different tools, different instructions, and different specialized capabilities. They can be assigned different responsibilities. They can work independently where appropriate and coordinate when their work intersects.

The important architectural distinction is that the shared information is maintained as a common resource rather than repeatedly reconstructed as separate agent-owned representations. We also need to distinguish shared state from agent-specific state. An agent’s objectives, private reasoning, local working context, and individual decisions do not automatically become shared. The architecture needs to preserve those distinctions.

So we have three important elements: shared computational state; agent-specific perspectives and responsibilities; and coordination mechanisms for managing changes, dependencies, and composed results. That is the foundation of FractiSI Multi-Agent.

Let’s look a little more closely at Tiny Gateway. The objective of Tiny Footprint is not simply to compress information. It is to reduce the amount of duplicated computational representation required when multiple agents work with overlapping information. Tiny Gateway provides the mechanism for accessing and working with that shared structure.

This changes the economics of adding agents. In a conventional architecture, adding an agent may introduce another collection of context, retrieval, memory, and synchronization requirements. In a shared-world architecture, additional agents can reuse infrastructure and information that already exist.

That doesn’t mean adding agents is free. Every agent still consumes model inference, computation, and potentially additional communication. And shared infrastructure itself has costs. But we have an opportunity to reduce the incremental cost associated with duplicating the world each agent needs to understand.

This is why we call it Tiny Footprint. We want the shared world to remain small while the number and capabilities of its participants can grow.

I want to clarify what FractiSI Multi-Agent is and what it isn’t. FractiSI is not another foundation model. It is not intended to replace Cursor, Claude Code, VS Code, or Git. Those tools provide valuable capabilities for developing software. FractiSI operates alongside them.

It is a coordination architecture for multi-agent engineering. The agents can use the models and tools they already work with. FractiSI provides the shared computational environment in which their work can be coordinated.

This distinction matters because we are not trying to win by creating another individual coding assistant. We’re addressing a different layer of the problem: how do we make many capable agents work together efficiently on the same complex project? And the same architectural question extends beyond software engineering.

Part III · Why the architecture matters

Beyond smaller data

  • Goal: greater agent density in a fixed budget
  • More specialization · more frequent coordination · finer task split
  • Collective stays on the same current information

Not only cheaper agents — larger, more capable collectives made practical.

This is probably the most important distinction in our work. The opportunity is not simply smaller data. It is greater agent density within a fixed infrastructure budget.

Consider what happens if we reduce the resources required to maintain overlapping representations of the same world. We may be able to support more agents. Those agents may be able to specialize more deeply. We may be able to increase the frequency of coordination. We may be able to assign more tasks to specialized agents rather than asking a small number of agents to perform everything. And we may be able to keep more of the collective working against the same current information.

This leads to a larger possibility. An architectural improvement that initially looks like a memory or storage optimization could change the number of agents we can practically deploy. And that can change the kinds of multi-agent systems we can afford to build.

The important distinction is: we are not just trying to make existing agents cheaper. We are trying to make larger and more capable agent collectives practical.

Part III · Why the architecture matters

What should we measure?

Resources

Memory · storage · CPU · tokens · communication

Operations

Time · latency · throughput · redundancy · coordination

Quality

Accuracy · completeness · consistency · conflicts · correctness

Scale & collective

Agent count · density · convergence · composed results

A memory win that slows work or hurts accuracy is not an improvement.

We need to evaluate this architecture against meaningful outcomes. A memory benchmark alone isn’t sufficient. If we use less memory but take longer to complete a task, we haven’t necessarily improved the system. Likewise, if we support more agents but produce less accurate results, that isn’t a meaningful improvement.

So our evaluation needs multiple dimensions: resource consumption; operational performance; quality; scalability; and collective performance — time to convergence, quality of composed results, ability to handle interdependent tasks.

We want to know whether FractiSI provides an advantage in the actual work being performed. Not simply whether it stores information more efficiently.

Receipts · Expedition 002 · Research · Run benchmark locally

Our experimental approach is to compare two architectures: a conventional multi-agent system and a FractiSI shared-world system. We want to hold the task, information, models, tools, and agent responsibilities as consistent as possible. The architectural difference becomes the independent variable.

In the conventional system, agents maintain and exchange their respective representations. In FractiSI, agents work through the shared computational substrate. We then evaluate the outcomes.

Important questions: Does FractiSI reduce duplicated information? Communication overhead? Task completion time? Preserve or improve accuracy? Improve conflict resolution? And how does performance change as we increase the number of agents?

We need to test at multiple scales. A system with three agents may show very different behavior from one with thirty or one hundred agents. We also need to test situations where agents modify overlapping information, where information changes rapidly, and where agents disagree. A shared-world architecture must demonstrate that it can manage those conditions reliably. The goal is a fair, reproducible comparison—not a demonstration designed to favor our own architecture.

Part IV · Applications

Example · software engineering

  • Twenty agents: architecture, research, code, test, security, docs, perf, integration
  • Interdependent: one change ripples; ownership and conflicts must be explicit
  • Shared project state as the computational environment

Agentic engineering without each agent rebuilding the whole project.

Let’s return to software engineering because it is an immediately understandable application. Imagine a team of twenty AI agents working on a major software project — architecture, research, coding, testing, security, documentation, performance, integration. Each has a specialized responsibility. But their work is interconnected.

A change to one component may affect several others. A test result may change priorities. A security finding may require modifications to code written by another agent. A new architectural decision may affect the entire project.

With conventional approaches, we need to coordinate these dependencies across agent contexts and messages. With FractiSI, we want the project state to become a shared computational environment. Agents can work against relevant portions of that environment. Their changes and findings can become available to the other participants according to the coordination rules. Ownership, dependencies, and conflicting modifications need to be managed explicitly.

The result we are pursuing is a development environment where many agents can contribute to the same project without each needing to reconstruct the entire project independently. This is why FractiSI is particularly relevant to agentic engineering.

Reliability, security, audit, latency, human authority — open research, not claimed solved.

Now let’s move beyond software. Consider air traffic coordination. There are aircraft, flight plans, weather systems, airports, controllers, safety constraints, and changing conditions. Different agents could monitor different aspects of the situation — weather, trajectories, potential conflicts, alternative routes, safety constraints, airport operations. They have different responsibilities, but they are working within the same evolving airspace.

The same principle applies to defense and situational awareness. Different sensors, analysts, intelligence systems, logistics teams, and operational agents may contribute different information about a shared operational environment. The architecture could provide a common computational substrate through which those participants work.

There are important additional requirements in these domains: reliability, security, access controls, auditability, latency guarantees, and human authority over consequential decisions. We aren’t claiming that FractiSI has already solved those mission-critical requirements. We’re identifying these as important application areas where shared-world coordination deserves rigorous investigation.

The underlying architectural problem is similar: many specialized participants; one changing environment; interdependent decisions.

I’d like to return briefly to the broader interests of this symposium. Our work is focused on computational architecture for multi-agent coordination. The Active Inference community brings an important perspective on agents operating in environments through perception, inference, and action. We see a useful area for exploration at the intersection of these interests.

Consider multiple agents operating in a shared environment. Each may have different observations, beliefs, preferences and objectives, and selected actions. The question for FractiSI is how the computational representation of their shared environment can support those activities.

What information should be represented once? What should remain agent-specific? How should updates become available? How should agents deal with uncertainty, conflicting information, and different interpretations? And how can the architecture support coordinated action without eliminating individual perspectives?

These are questions we believe are worth exploring with researchers and practitioners working on Active Inference and related approaches. We see this as an opportunity for interdisciplinary experimentation, not a claim that the two frameworks are interchangeable.

Part V · Connection to the symposium

Does sharing the world change what agents can do?

  • Efficiency vs possibility
  • More specialists · finer monitors · more simultaneous coordination
  • Larger collectives may unlock capabilities small fleets cannot

Does the architecture change the feasible design space?

This brings us to the question behind the entire project. Does sharing the world simply make multi-agent systems more efficient? Or can it change what those systems can actually do?

Suppose we can reduce the cost of adding agents. We might support more specialized participants, distribute responsibilities more finely, allow agents to monitor different aspects continuously, coordinate more activities simultaneously, and make larger collectives economically practical. And those larger collectives could have capabilities that are difficult to achieve with a small number of agents.

This is the distinction between optimization and possibility. We don’t want to stop at asking whether we can make an existing multi-agent system smaller or faster. We want to investigate whether changing its underlying architecture changes the feasible design space — the possibility of more intelligence working together, within the same computational budget.

There are still important questions to answer. How should shared state be partitioned? How should ownership and permissions work? What information should remain private to individual agents? How do we prevent a shared substrate from becoming a bottleneck? How do we handle simultaneous changes? How do we represent disagreement? How does the architecture behave when agents fail or produce incorrect information? And how do these choices affect the quality of collective outcomes?

These are not peripheral engineering details. They are central to making a shared-world architecture useful. We want to evaluate the system in real applications, with realistic workloads, and against credible alternatives. We also want to make the architecture and experimental methodology accessible so that others can reproduce and challenge our findings. There is much more to discover.
